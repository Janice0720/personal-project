## 一、現有摘要是否足夠

### 結論

現有的 `大語言模型開發.md` 已涵蓋第五章的大多數主題，但**不適合直接做成 14 張投影片講 1–1.5 小時**。

- 若每張只講 2–3 分鐘，14 張約能支撐 30–45 分鐘。
- 若硬把 90 分鐘內容塞進 14 張，每張會同時出現大量文字、公式與程式碼，學生難以跟上。
- 建議改為 **31 張、由一位報告者連續講授約 80–85 分鐘**。
- 60 分鐘版本可略過本文件標成「85 分鐘完整版」的補充內容。

### 現有摘要做得好的地方

1. 已抓到章節的四條主線：LLM 與 Llama、Llama 2-Chat、模型結構、權重與參數量。
2. 有把附送 Notebook 的 `AutoModelForCausalLM`、`sum(p.numel())`、`LazyUnpickler` 納入。
3. 有安排白話比喻，適合非純資訊背景的課堂。
4. 有意識到要把數學公式和硬體需求連結起來。

### 必須補強或修正的地方

| 問題 | 影響 | 建議處理 |
| --- | --- | --- |
| 14 張投影片過度濃縮 | 無法同時看懂公式、架構與長程式碼 | 拆成約 30 張，每張只回答一個問題 |
| RMSNorm、SwiGLU、RoPE 的推導超出課本篇幅 | 容易讓聽眾誤以為這是本章主體 | 保留概念與在程式結構中的位置，不做長篇數學推導 |
| RAG、LoRA、GGUF/INT4 不在第五章 | 會偏離「教這一章」的任務 | 移到最後一張延伸閱讀，最多 2 分鐘 |
| GPT-3.5 的「175B、28 層、2048 hidden units」彼此不合理 | 可能把課本中的可疑資訊當成已確認事實 | 投影片改寫為「課本如此描述，公開技術細節有限」，不要拿來做架構比較或計算 |
| 把 13.48 GB 檔案大小直接稱為最低 VRAM | 磁碟檔案大小不等於實際推理顯存 | 明確區分 decimal GB、binary GiB、權重大小、載入開銷與 KV cache |
| 把 `rotary_emb.inv_freq` 計入可訓練參數 | 它在不同 Transformers 版本可能是 buffer，不一定由 `model.parameters()` 統計 | 將「公式估算」「參數 API 結果」「檔案位元組」列成三種口徑 |
| 摘要稱 `LazyUnpickler` 可毫秒解析、記憶體接近零 | 課本未提供效能測量 | 改成「不讀取完整 tensor payload，降低記憶體需求」，不宣稱固定速度 |
| 書中與 Notebook 為舊版 `.bin` 範例 | 現在常見模型也使用 `safetensors` | 教學時先忠實解釋 `.bin`，再提醒方法不可直接套到 `safetensors` |
| 程式碼太長 | 一張放完整程式會完全不可讀 | 投影片只放關鍵 6–12 行，完整程式以 Notebook QR code 或附錄提供 |

## 二、建議教學目標

課程結束時，同學應能：

1. 說明預訓練語言模型與大語言模型的關係。
2. 比較 Llama 1 與 Llama 2 的資料量、上下文長度與 GQA 差異。
3. 描述 Llama 2-Chat 從 SFT 到 RLHF 的訓練流程。
4. 從 Hugging Face 模型輸出辨認 embedding、decoder layer、attention、MLP、norm 與 `lm_head`。
5. 依矩陣形狀估算 Llama 2 的參數量與權重位元組數。
6. 解釋 Hugging Face sharded checkpoint、index JSON 與 `.bin` 內部結構。
7. 說明 `LazyUnpickler` 如何只讀 tensor metadata，而不載入完整權重內容。

## 二之一、如何用這份 Markdown 生成 PPT

可以直接以這份 Markdown 作為 PPT 的內容規格。產生投影片時，解析規則如下：

- 每個 `####` 標題代表一張投影片。
- `[核心]` 代表 60 分鐘精簡版一定保留。
- `[完整版加講]` 代表 85 分鐘完整版才加入。
- `[核心・課本附碼]` 代表兩種版本都保留，而且必須引用附贈 Notebook 的程式碼。
- 產生 PPT 後，刪除標題中的方括號標籤；這些標籤只用來控制版本，不顯示給觀眾。
- `畫面` 是投影片上真正要呈現的內容。
- `講者重點`、`講者補充`、`開場句` 放入 speaker notes，不要全部塞在投影片上。
- Markdown code block 轉成等寬字型程式碼區塊，保留縮排與語法顏色。
- `來源`、`程式來源` 放在 speaker notes；若老師要求可見引用，再放到投影片頁尾。

### 兩種版本的辨識方式

| 版本 | 投影片 | 做法 | 預估時間 |

### E. 參數量與位元組計算

#### 22. [核心] 參數量就是矩陣元素數

- **時間**：2 分鐘
- **畫面**：一個 `Linear(4096, 11008, bias=False)`。
- **計算**：`4096 × 11008 = 45,088,768` 個參數。
- **講者重點**：`bias=False` 代表不用再加 11,008 個 bias；形狀相乘就是這一層權重數。
- **來源**：課本 p.136–138。

#### 23. [核心] 每層 Attention 與 MLP 的參數

- **時間**：4 分鐘
- **畫面**：分兩步計算。
  - MHA：`4d²`，來自 Q、K、V、O 四個矩陣。
  - SwiGLU MLP：`3d × d_ff`，來自 gate、up、down 三個矩陣。
  - Norm：每層兩個長度為 `d` 的向量。
- **講者計算**：實際代入 7B 的維度，比較 attention 與 MLP 的參數量，帶出 MLP 佔比更大的原因。
- **來源**：課本 p.138，5.8.2。

#### 24. [核心・課本附碼] Llama 2 7B 總參數公式

- **時間**：4 分鐘
- **畫面**：公式拆成「輸入 embedding + 32 層 + final norm + lm_head」。

```text
P = Vd + L(4d² + 3d·d_ff + 2d + 64) + d + Vd
```

```python
V = 32000
d_model = 4096
d_ff = 11008
L = 32

nparams = (
    V * d_model
    + L * (4 * d_model**2 + 3 * d_ff * d_model + 2 * d_model + 64)
    + d_model
    + V * d_model
)
print(nparams)
```

- **代入**：`V=32000, d=4096, d_ff=11008, L=32`。
- **課本口徑結果**：6,738,417,664。
- **重要註記**：公式中的 `+64` 對應 `rotary_emb.inv_freq`，但它在不同版本可能是 buffer，不一定屬於 `model.parameters()`；必須說明統計口徑。
- **來源**：課本 p.138–139，表 5-7；參數量 Notebook 第一格。

#### 26. [核心] 參數、檔案大小與顯存不是同一件事

- **時間**：2 分鐘
- **畫面**：四層區分。
  1. 參數量：元素個數。
  2. 權重 bytes：元素個數 × dtype bytes。
  3. 檔案大小：權重外加容器與 metadata。
  4. 執行顯存：權重外加 activation、KV cache 與框架配置。
- **數值示例**：6,738,417,664 個 FP16 元素約為 13.4768 GB，或 12.5513 GiB。不要把 GB 與 GiB 混用。
- **講者重點**：推理所需顯存不能只用 checkpoint 檔案大小斷言。

```python
def persistent_load(self, pid):
    assert pid[0] == "storage"
    data_type = pid[1].data_type
    filename = self.data_base_path + "/" + pid[2]
```

```python
def lazy_rebuild_tensor_v2(storage, offset, size, stride,
```
